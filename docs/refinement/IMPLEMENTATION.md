# Consulting experience refinement

Implemented on 15 October 2026 in the existing repository. The [pre-implementation audit](AUDIT.md) explains the starting architecture and plan. Existing service boundaries, reference patterns, projects and historical snapshots are preserved. No commits, staging, pushes, worktrees or database resets were used.

## Discovery and assessment readiness

`exploration.ts` adds optional motivation, interests, strengths, time/resources, experiment style and comfort questions. The uncertain journey uses these instead of asking for an existing process or investment range. After two skipped/unknown responses it offers concrete experiment categories. After three exploration responses, including uncertainty, a qualified exploration profile is available; the guided sequence ends after four. This is readiness to explore, not evidence of a business opportunity. Reports do not invent skills, resources, interests, income or demand. Skipped/unknown text is excluded from the profile.

An idea can receive initial validation guidance once a meaningful idea description exists. Existing-business and defined-solution journeys retain evidence-based workflow/scoping questions, conflicts and specialist boundaries. Explicit operational details in legacy uncertain projects retain their existing business recommendations. Users can change their starting situation with the same validated answer mutation path. The planner cache version changed, while the persisted discovery definition remains `1.0.0` so historical sessions remain readable.

Recognition runs across confirmed answers. Instagram, WhatsApp Business and a phone calendar can be recognised from a business description rather than requiring a separate tools answer. Technical confidence, mobile management, affordability and maintenance preferences are constraints. “Simpler booking” is recognised as an objective, rather than being excluded by the word “simple”. Rich booking-volume/friction descriptions supply booking details and avoid asking the same question again. Readiness uses natural explanations; structured missing-field keys remain available separately for evaluation.

**Start from beginning** is available to guests and account users. A revision-checked endpoint resets the current session's Discovery answers. It retires guided evidence, preserves Chat-confirmed facts except the journey selection, supersedes derived summaries and advances knowledge revision. Its confirmation explains the scope. Conversations, reference knowledge, account preferences, resources and immutable report snapshots are not deleted. Existing chat facts can still guide the restarted journey. Changing modes preserves original evidence as history through the existing mutation pipeline.

## AI and conversational behaviour

Cloudflare Workers AI and local deterministic guidance remain the supported providers. No credentials were copied into frontend code or documentation. Both the guest route's unconditional mock flag and the service's unconditional guest exclusion were removed. `AI_ALLOW_GUEST_REMOTE` can disable guest model use independently. It defaults to true; actual external inference still requires `AI_PROVIDER=cloudflare`, `AI_ALLOW_REMOTE=true`, valid server credentials, quota, allowed input and non-sensitive context. Existing session/day quota reservation and origin/rate restrictions remain.

Questions beginning with an advice/interrogative form cannot become fact proposals, even if a model returns an update. Conversational output is no longer overwritten when proposed facts are duplicates. Ordinary suggested details are collapsed in Chat; consequential conflicts remain open for confirmation. Existing explicit confirmation remains the authority for changing confirmed information. Local guidance explains exploration and appointment-booking options, qualifies website need, subscriptions, calendar compatibility and reminder channels, and asks one relevant follow-up. It is clearly labelled local guidance.

Timeouts receive a distinct diagnostic code and user recovery message. Unqualified calendar integration claims are rejected by a dedicated reply guard. Provider HTTP/schema/transport failures are logged without prompts, private content or tokens. User messages and local replies remain persisted through the existing transactional path. The composer shows the established mascot head and three dots with a minimum 700ms transition after starting the request; CSS respects reduced motion. Empty conversation clearing shows a notice; nonempty clearing retains the existing explicit confirmation and archive semantics.

### Context and provenance

There is no second conversation or fact store. `DiscoverySession`, `DiscoveryAnswer`, `Evidence`, `ConversationSummary`, immutable `ReportSnapshot`, account preferences and project-owned resources remain distinct authorities. Confirmed answers take precedence over historical references and suggestions. Existing project conversation retrieval is owner-and-plan scoped. New conversation creation carries confirmed context using the existing API.

Saved report discussion passes an explicit report UUID. The backend verifies that report belongs to the same owner and project before reserving inference usage, then includes bounded report content as historical advice. Automatic report retrieval now includes recommendation summaries instead of only the original business description. Up to three matching extracted resources enter bounded personal memory, labelled untrusted references. They cannot become confirmed facts or override instructions. Sensitive memory, including selected reports and sources, is checked before remote quota reservation and again by the provider. Model preferences guide explanation depth and implementation comparisons; project requirements and evidence remain authoritative. Deterministic assessments continue to compare existing tools before unjustified custom work regardless of an account preference.

## Navigation and visual design

The existing cream/off-white application shell is retained. Ellipsis precedes the kailor wordmark. The sidebar overlays the content, with a blurred backdrop, Escape dismissal, focus containment, focus restoration and a lightweight desktop rail. The existing conversation-list component now appears under the active project in the sidebar; the main Chat dropdown is removed. New conversations and switching use existing project selection and creation APIs. Only the selected project's conversation list is fetched, with pagination.

Shared controls use light secondary surfaces, visible focus rings, consistent radii and reduced-motion rules. Mobile Discovery uses a smaller mascot so its text composer remains practical. Chat keeps an internally scrolling transcript and anchored composer. Settings uses spaced labels, model configuration disclosure and expandable privacy details. Account supports an explicit guest-continuity invitation and real transfer controls after sign-in.

## Reports, history, canvas and PDF

The recommendation engine remains deterministic and evidence-based. New reports have an explicit assessment type and presentation version. Exploration/idea reports describe uncertainty, illustrative directions and low-commitment validation. Business/defined-solution reports contain overview, current situation, challenges, recommendations, alternatives, benefits/trade-offs, costs, dependencies/risks, roadmap, decisions and supporting evidence. Reports are preliminary and explicitly not human-reviewed. No AI-authored or consultant-reviewed report is falsely claimed.

`ReportReader` is shared by active and saved reports, replacing the fixed seven-slide carousel with a reading column and section links. Supporting evidence is expandable. `customerReport` is a read-only adapter for older stored JSON; it hides internal status fields/reference dumps without mutating snapshots. Retrieval favours actual domain matches, filters irrelevant service patterns when an independently supported direction exists, and deduplicates equivalent patterns. New reports keep internal reference metadata for auditing but present a concise relevance note. PDF uses the same customer projection and report sections. Chat and Discovery use a metadata-only report freshness endpoint rather than downloading report evidence after every turn. History is paginated, displays meaningful titles/date/type/summary, and supports opening, discussing and downloading the specific report. A new assessment still requires a new knowledge revision; existing snapshots are never rewritten because application wording changes.

`canvas-model.ts` produces a structured graph of reported tools/channels, desired outcomes, proposed components, exploratory options and dependencies. Booking recommendations produce capability steps for availability, reminders and calendar compatibility, all qualified by provider verification. It is a generic appointment-workflow branch, not a nail-specific workflow. Nodes and edges are selectable keyboard controls with a detail panel, evidence, alternatives and a Chat discussion action. Discussion inserts a component-specific question; it does not silently confirm the component. No diagramming dependency or duplicate persisted canvas state is introduced. Canvas represents current knowledge or a matching saved assessment; it does not provision third-party services.

## Sources and document handling

An additive `ProjectSource` table stores plan-owned notes, supplied URLs and extracted UTF-8 `.txt`/`.csv` content. Resource lists are paginated; report lists do not load full report JSON into the browser. A file must be at most 64KB and contain at most 16,000 characters, decode as UTF-8 and pass nonempty/control-character/instruction checks. Only successful extraction yields a ready resource. CSV is reference text; no formulas execute. Each project is limited to 100 resources, serialized under the project lock during insertion. Storage uses the existing private PostgreSQL database. Routes enforce ownership, reject archived mutations and support deletion. Plain text is rendered as escaped text, never HTML. Supplied URLs must be HTTP(S), without embedded credentials, and remain explicitly **not retrieved or verified**; the server does not fetch them, avoiding an SSRF path.

**Binary PDF/Word ingestion is unavailable.** The repository had no upload or extraction pipeline. This implementation deliberately offers only supported text/CSV inputs. Safe PDF/DOCX support still needs bounded server extraction, sandbox/time/memory controls, malformed/encrypted document handling and deployment packaging. The interface and API explicitly reject these formats rather than claim analysis. Reference text is not a fact authority and does not itself change an existing assessment; confirm any resulting findings in Chat or Discovery before generating another version.

## Guest continuity and security

Guest access remains a nonrenewing 24-hour HTTP-only cookie, separate from account authentication. Expiry ends browser access; records are not automatically purged. Core guest functionality remains available without sign-in. Email registration/login and member/admin checks are preserved. **GitHub OAuth was absent in the audited repository and remains explicitly unavailable.** No existing OAuth was replaced or broken; a real OAuth feature needs credentials and a separately verified callback/account-linking flow.

The guest Account page sends sign-in/registration back to the same guest Account route. A subsequent transfer requires explicit consent, the unexpired guest cookie and an authenticated account cookie. It locks the account, guest and project, updates project ownership and relies on the existing composite foreign key's `ON UPDATE CASCADE` to move every discovery/conversation atomically. Sources stay attached to the same project. Answers, evidence, reports, summaries and derived canvas inputs retain their IDs and content. Existing account projects/preferences are not overwritten. Guest selections are cleared and guest tokens revoked. An account-bound audit entry makes retries with the same operation key idempotent even after token revocation. There is no implicit merge on login and no recovery promise for expired guest access.

CSRF/origin validation, opaque tokens, secure production cookies, owner predicates, row/revision locks, model budgets and rate limits remain. No private project data is promoted into reusable case knowledge. No third-party integrations or pricing are represented as verified merely because a recommendation exists.

## Deployment

1. Back up PostgreSQL according to the deployment's normal policy.
2. Install the existing locked dependencies with Node >=22.12.
3. Run `npm run db:generate` and `npx prisma migrate deploy --config backend/prisma.config.ts`. The new migration only creates `ProjectSource` and its index/foreign key. No data reset or reseed is necessary. The root `db:migrate` script also runs the pre-existing founder-preservation helper; the refinement does not require changing account roles.
4. Run `npm run typecheck`, `npm test` and `npm run build`. Start the backend with `npm run start -w backend`; serve the built frontend with same-origin `/api` routing and HTTPS in production. Keep `.env` server-side.
5. Existing variables are documented in `.env.example`: `DATABASE_URL`, `HOST`, `PORT`, `APP_ORIGIN`, registration policy, Cloudflare provider/opt-in/account/token/model, timeout, session/day quotas, output/context limits and optional estimate inputs. `AI_ALLOW_GUEST_REMOTE=false` keeps guest inference local. No deployment script enables remote inference or billing automatically.
6. For an isolated browser preview, point `KAILOR_API_ORIGIN` at a separate local backend and set that backend's `APP_ORIGIN` to the frontend origin. This development-only proxy override is not a credential or production client setting.

Production TLS, database backups, storage lifecycle/purge policy, provider costs, auth recovery, OAuth and binary-document extraction remain deployment concerns. The single approved live synthetic request verifies transport and a conversational answer, not broad model quality or third-party integration compatibility. See [executed verification](TESTING.md).
