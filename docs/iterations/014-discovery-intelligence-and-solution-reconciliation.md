## Domain behaviour and precedence

`shared/src/project-intent.ts` contains reusable evidence rules for launch stage, website/social needs, application requests and exclusions, operational needs, booking deferral, and presence capability recognition. It is not a grooming persona switch. The original `specific` starting choice remains intact. Exact initial requirements are attributed to their original answer; inferred presentation guidance is labelled for verification rather than asserted as vendor support.

The existing Discovery answers, explicit answer states, ConsultingBrief requirements/facts and Plan Canvas JSON remain the storage model. There is no new table or competing project-memory store. Original facts, requested capabilities, requirement priority (essential/optional/deferred/unconfirmed), constraints/exclusions, genuine unknowns, user proposals, edits, selections and immutable assessment snapshots retain their existing provenance boundaries. New launch-answer keys participate in the same fact pipeline.

`projectSolutions` is the common living projection for Canvas, reasoning exports, consultancy requests and Chat. `createReport` uses that projection to reconcile new assessments as well. A website does not inherit dispatch/GPS capabilities; Instagram does not inherit website pricing/contact-page capabilities. Shared branding remains relevant to both. Pending added capabilities are saved even if Add to scope has not been pressed; duplicate labels are suppressed. Removed capabilities disappear from subsequent projections and deferred capabilities retain their deferred priority.

Stable record IDs are separate from current category. A uniquely matched legacy correction (for example, a retired `webapp` ID refined into a website) retains its identity when the new classifier recognises a website, without creating a second website tile. Ambiguous retired selections retain the existing unresolved-selection safeguard rather than being silently reassigned.

Scope revisions are derived per solution from its actual content, requirements and constraints. Editing website scope therefore does not invalidate an unrelated Instagram scope. Selections survive changes and require confirmation when their basis revision differs. Request submission still validates account ownership, project/session association, project and solution revisions, duplicate references and unresolved selections on the server.

## Editing and review

A saved refinement is labelled “Refined by you · needs review”. This does not claim independent AI, consultant or vendor validation. Deterministic reconciliation runs on read and uses current category, known requirements, explicit priorities and attributed edits. A correction outside the recognised semantic vocabulary keeps the user's objective and capabilities, suppresses stale alternatives and requests scope review. No live reassessment service was added; an unavailable live provider therefore cannot discard a refinement or falsely validate it.

Full edited objectives stay in `objective`; tiles and combined request summaries use a complete concise sentence or a bounded neutral description. The modal exposes the full objective. Done editing asks before discarding unsaved edits; saving retains a pending additional capability. Existing source corrections continue through the existing answer-correction mechanism.

## Assessment completion, reports and PDFs

Discovery switches to a saved-assessment state even when a relevant next question remains. It uses the supplied `/mascot/other/kailor-smiling.png`, exposes Explore your assessment and Continue discovery, and retains Chat access. Preparation displays the existing busy treatment, prevents duplicate action and only enters success after the assessment request succeeds. Failure retains answers and allows retry. Continue discovery prioritises the planner's next relevant gap.

Existing assessment/database snapshots are never rewritten. New knowledge or Canvas changes make the saved assessment stale; the existing Analysis notice offers a new version. Deliberately opening a historical assessment continues to discuss that snapshot. Current reasoning downloads use the current solution projection and show user-refinement review status, correct alternatives and practical next steps. Internal scope hashes and fact IDs are retained for server checks, not printed as user-facing revision metadata. PDF evidence is grouped by source, capability provenance is deduplicated and empty sections are omitted.

## Consultancy and account continuity

The existing combined-selection workflow, revision validation, optimistic conflict checks, notes storage and idempotent submission remain. The review uses current scope and truthful refinement status. `resume=consultancy` is carried through Account, sign-in/create-account return paths and explicit guest-transfer consent. Successful transfer returns to Canvas with the review open; the user must review and submit intentionally. Notes remain in the existing tab's project-keyed session storage and project/solution identities remain server-owned. There is no automatic submission, invoice, engagement or external consultant notification.

The isolated integration suite verifies existing controlled-account transfer, ownership protection, combined request persistence, submission idempotency and scope conflicts. Public registration and guest invalidation after transfer are covered by the existing account/guest suites. Browser QA verified fresh guest entry, persisted skips, assessment success, actual generated Analysis, website scope, a pending Canvas-only capability saved without Add to scope, the reasoning download, and current-solution Chat handoff. Browser QA also verified two independent selections, combined review with the refined status, notes persistence after opening Account and returning, and an authentication return URL retaining `resume=consultancy`. ## Known limits and deferred work

Semantic extraction remains deterministic, vocabulary-based and deliberately conservative. Unrecognised freeform requirements remain in the full objective and can be added explicitly as capabilities; they are not asserted as independently reassessed. Conflicting complex natural-language corrections can still require clarification. Review confirmation acknowledges a selected scope; it does not validate implementation feasibility. The legacy alias rule only resolves an unambiguous current category match.

No changes were made to account-wide workspace identity, new-project entry, consultant messaging, in-app notifications, implementation tracking, web research, resource uploads or account-wide work overview. Solution canvas visual refinement, Analysis visual redesign and Sources visual redesign remain future iterations. The approved white/off-white surfaces, typography, controls, sidebar, authentication pages, existing artwork, tile/modal styling and responsive CSS are preserved.
