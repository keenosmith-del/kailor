# Discovery engine

Current production progression uses `discovery-planner.ts`, not catalogue order. Definition `1.0.0` retains existing IDs and single/multi/text validation, with optional application scope, general workflow, website status and URL inputs. `nextQuestion` remains a compatibility helper for legacy catalogue tests only.

The planner builds a normalized context from confirmed saved answers and evidence, detects source-linked language possibilities, removes answered/indirectly described gaps, ranks relevant questions by decision impact and returns readiness alongside the next question. Exact requirements begin with a description and application scope; new ideas avoid assumptions about current systems; vague users clarify their situation; unfamiliar industries receive general workflow questions without needing a scenario match.

Rank priorities and limitations are documented in [iteration 003](../iterations/003-adaptive-intelligence.md). They are explainable ordering values, not confidence probabilities. Approved references can add a small workflow priority and labelled clarification hints. Once there is enough evidence for a preliminary direction, optional commercial inputs do not prolong discovery. Material follow-ups can remain while assessment preparation is already available.

The session row stores revision-bound `contextState` and `planState`. Plans include complete adapted definitions, priorities/reasons, context, readiness, prompts and case/version provenance. Repeated reads replay the saved plan. Answer/chat/confirmation mutations rebuild projections under the same row lock and revision checks as authoritative answers. Historical null projections initialize lazily. The new JSONB columns require the additive iteration 003 migration; existing records are preserved.

A guided answer or accepted chat proposal is confirmed. Semantic signals derived from prose remain labelled possibilities, cite source keys and never become confirmed standardized fields automatically. Explicit selections (including none/skips) override these signals. Branch pruning excludes dependent details from trigger extraction to prevent stale self-activation. Inactive evidence remains available for audit, while irrelevant pending proposals are retired.

Individual and grouped conversational confirmations share the answer writer. Group review is atomic, validates every field, and advances revisions per reviewed fact. Exact dismissed key/value candidates do not recur without a changed candidate; a new pending value supersedes earlier pending values for its field. Accepting corrections is an explicit user action.

Readiness requires understood context, an objective/problem/requirement, and at least one evidence-supported catalogue direction. Unknown constraints, budget, tools and timing are reported, not invented. State/reasons/uncertainties are persisted; there is no percentage. Assessment preparation and Explore the analysis are separate explicit actions, and changed revisions make previous immutable reports stale.

The frontend renders the backend plan, keeps existing transitions, supports Back and a simple answer-review disclosure, and exposes preliminary preparation during follow-ups. Unsaved input is local component state; changing views can discard it. Full historical interactive replay and AI-authored follow-up questions remain future work. Current adaptations are deterministic templates; simulation paths record their actual wording and answers.
