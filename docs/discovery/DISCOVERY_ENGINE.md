# Discovery engine

Current production progression uses `discovery-planner.ts`, not catalogue order. Definition `1.0.0` retains existing IDs and single/multi/text validation, with optional application scope, general workflow, website status and URL inputs. `nextQuestion` remains a compatibility helper for legacy catalogue tests only.

The planner builds a normalized context from confirmed saved answers and evidence, detects source-linked language possibilities, removes answered/indirectly described gaps, ranks relevant questions by decision impact and returns readiness alongside the next question. Exact requirements begin with a description and application scope; new ideas avoid assumptions about current systems; vague users clarify their situation; unfamiliar industries receive general workflow questions without needing a scenario match.

Rank priorities and limitations are documented in [iteration 003](../iterations/003-adaptive-intelligence.md). They are explainable ordering values, not confidence probabilities. Approved references can add a small workflow priority and labelled clarification hints. Once there is enough evidence for a preliminary direction, optional commercial inputs do not prolong discovery. Material follow-ups can remain while assessment preparation is already available.

The session row stores revision-bound `contextState` and `planState`. Plans include complete adapted definitions, priorities/reasons, context, readiness, prompts and case/version provenance. Repeated reads replay the saved plan. Answer/chat/confirmation mutations rebuild projections under the same row lock and revision checks as authoritative answers. Historical null projections initialize lazily. The new JSONB columns require the additive iteration 003 migration; existing records are preserved.

A guided answer or accepted chat proposal is confirmed. Semantic signals derived from prose remain labelled possibilities, cite source keys and never become confirmed standardized fields automatically. Explicit selections (including none/skips) override these signals. Branch pruning excludes dependent details from trigger extraction to prevent stale self-activation. Inactive evidence remains available for audit, while irrelevant pending proposals are retired.

Individual and grouped conversational confirmations share the answer writer. Group review is atomic, validates every field, and advances revisions per reviewed fact. Exact dismissed key/value candidates do not recur without a changed candidate; a new pending value supersedes earlier pending values for its field. Accepting corrections is an explicit user action.

Readiness requires understood context, an objective/problem/requirement, and at least one evidence-supported catalogue direction. Unknown constraints, budget, tools and timing are reported, not invented. State/reasons/uncertainties are persisted; there is no percentage. Assessment preparation and Explore the analysis are separate explicit actions, and changed revisions make previous immutable reports stale.

The frontend renders the backend plan, keeps existing transitions, supports Back and a simple answer-review disclosure, and exposes preliminary preparation during follow-ups. Unsaved input is local component state; changing views can discard it. Full historical interactive replay and AI-authored follow-up questions remain future work. Current adaptations are deterministic templates; simulation paths record their actual wording and answers.

## Iteration 004: quality, response states and recovery

`input-quality.ts` evaluates guided text at the mutation boundary and conversational candidates before evidence creation. Results contain stable disposition/issues, accepted/usableFacts/clarificationRequired, explanation and recovery. Obvious placeholders, repeated nonsense, unsupported role instructions and empty answers are rejected; unknown terminology and other languages are not rejected by vocabulary. Ambiguous or uncertain descriptions can be saved without supplying factual evidence. Text is retained verbatim.

Answers distinguish `answered`, `unknown`, `not_applicable` and `skipped`. The persisted plan additionally projects `not_presented`, `awaiting_answer` and `irrelevant` for pruned branches. These are planner states, not browser view telemetry. Historical skipped answers and exact Not applicable values are migrated; historical uncertainty is also interpreted conservatively at runtime. Skips imply no negative fact. Required text questions allow explicit uncertainty, while required selections retain validation.

`evidence-policy.ts` determines useful situation/objective evidence, supported directions, material conflicts, domain limitations and unknowns independently of recommendations and case counts. `discovery-readiness.ts` wraps that decision for planner, assessment, chat and Canvas. An industry alone, vague improvement goal or selected budget cannot create readiness. Missing financial details do not block a proportionate preliminary direction. Deeper readiness requires useful scope, tools and constraints; it is still a draft requiring review.

Planner version `reliability-2` persists completion: `in_progress`, `clarification_required`, `preliminary_available`, `deeper_available`, `exhausted`, `unsupported`. A missing next question never implies success. Catalogue clarification is bounded; skipped/unknown answers are not endlessly repeated. Explicit Tell kailor more reopens a contextual clarification input. Conversation preserves the same session. Restart creates a fresh identity while retaining the original history.

Material website/booking/preference contradictions require confirmation. Guided conflicts return a saved pending proposal and refreshed revision; no confirmed fact is silently overwritten. Confirmed corrections retire conflicting evidence while preserving history and other still-relevant proposals. Historical/hypothetical clauses do not become current status. Budget versus scope tensions are tradeoffs, not automatically logical contradictions. The frontend retains text after validation errors, offers required-text uncertainty and recovery actions, and contains no Review your answers control.

## Contextual planner 005

Definition `1.0.0` remains compatible through additive optional question IDs; planner `contextual-3` lazily rebuilds older projections. Contextual gaps cover offline/sync, record capture, roles, reporting, integrations, existing booking capabilities, content ownership, alternatives and a useful first version. Their ranking derives from current needs, not industry pathways. An approved case adds at most 80 priority points only to an independently relevant gap; offline feasibility retains priority. Skipped/unknown/answered IDs do not repeat. Planned-question history survives view changes but is not a presentation-event audit. A founder-authorized model may only reword the current contextual text gap after an explicit follow-up request; definition/type/ID/quality/topic/revision validation and persisted provenance apply. Normal discovery stays local. See the [selection policy and limits](../iterations/005-contextual-intelligence.md).

## Conversation as an assessment path

Conversation can confirm sufficient evidence and prepare an assessment without selecting a guided starting stage. The shared planner suppresses that generic stage question once the situation is known. Shared evidence sufficiency, skipped states, pending conflicts and knowledge revisions remain authoritative. Explicit confirmation of a website replacing an application revises scope and report freshness; chat activity alone does not. See [iteration 006](../iterations/006-conversational-intelligence.md).
